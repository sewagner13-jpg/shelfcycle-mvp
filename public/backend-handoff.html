Backend-oriented project context for an agent reviewing the ShelfCycle MVP, daily brief pipeline, local Mac Messages integration, Gmail triage, and verified ShelfCycle action flow.

Prepared from the current working session on May 5, 2026. This packet intentionally contains no OAuth tokens, API keys, Gmail content, or private message bodies.

Primary backend problem: the app can generate review packets and preview ShelfCycle actions, but real ShelfCycle execution is incomplete. Recent health check showed 72 review packets and 0 executable actions because the backend only supports a narrow customer-note path when a single matched ShelfCycle customer ID is available.

1. Product Goal

Build a ClearEdge operating assistant that reads Gmail and Mac-local Messages, summarizes business-relevant activity, identifies next actions, and lets Sean verify any proposed ShelfCycle write before it is saved. The system should consolidate information and triage work, not generate replies automatically.

Non-negotiable behavior

  • Do not create ShelfCycle records without explicit user review and approval.
  • Do not write to Apple Messages or Gmail. Messages are read-only; Gmail is read/send only for the final brief.
  • Do not store unnecessary personal text-message content. Store structured summaries and source metadata instead.
  • Hosted Netlify cannot read Mac Messages. Mac Messages require the local runner on Sean's Mac.
  • Run validation and deploy at the end of completed builds unless Sean explicitly says not to deploy.

7. Backend Gaps Blocking User Value

A. ShelfCycle Action Execution Coverage

The backend now has an action router and approval-first submission endpoint. The remaining blocker is live, screen-tested execution coverage for every ShelfCycle action type. The UI should continue to distinguish executable actions from preview-only actions.

Needed action types:

  • customer_note: create a note on a resolved customer record.
  • supplier_note: create a note on a supplier/company record if ShelfCycle supports this route.
  • contact_create: create a contact under a selected customer/supplier/account.
  • product_create_or_update: create/update product record from SDS/TDS/catalog evidence after approval.
  • product_document_followup: attach or queue SDS/TDS/COA document handling.
  • pricing_record: queue or save pricing intelligence tied to account/product/supplier.
  • order_or_logistics_note: create shipment/order follow-up with container, PO, ETA, appointment, freight, or carrier details.

B. Target Resolution

Many review packets still need a human-selected ShelfCycle target because the exported knowledge bundle has names and domains but not reliable ShelfCycle ids. Customer notes can now resolve by selected label; other action types need stronger id/label resolution.

  • Use sender domain, contact list, customer export, supplier/product aliases, and knowledge bundle to suggest target accounts.
  • If target confidence is low, require user selection in the review UI before submit.
  • Do not mark an action executable until required target IDs and field mappings are present.
  • Store the selected target back into the local review packet so future action attempts are deterministic.

C. ShelfCycle Form Mirroring

The review landing page should mirror ShelfCycle fields before submission. This means the backend should expose an action schema per action type, not just a generic note preview.

{
  "actionType": "contact_create",
  "target": {
    "kind": "customer",

    "email": "",
    "phone": "",
    "role": "",
    "notes": "Evidence-derived context."
  },
  "requiresUserApproval": true,
  "isExecutable": true
}

9. Suggested Backend Design

Workflow run contract

workflowRun
  -> id, type, mode, status, actionState
  -> ordered steps[]
  -> metrics, artifacts, approval, logs, error

GET /api/workflows/runs
GET /api/workflows/latest
GET /api/workflows/run?id=...

Action router contract

collectExecutableActions(reviewAction)
  -> proposedActions[]
  -> each action has:
     - actionType
     - displayLabel
     - confidence
     - sourceEvidence
     - targetCandidates[]
     - selectedTarget
     - requiredFields[]
     - fieldValues
     - warnings[]
     - executable: boolean
     - submitEndpoint

Submission contract

POST /api/shelfcycle/submit-action
{
  "reviewActionId": "...",
  "token": "...",
  "actionType": "contact_create",
  "selectedTarget": { "kind": "customer", "id": "..." },
  "fields": { "...": "..." },
  "approvedByUser": true
}

The backend should validate the token, confirm the action is still valid, reject missing targets or required fields, run only the selected action, then return a result with a ShelfCycle URL if available.
